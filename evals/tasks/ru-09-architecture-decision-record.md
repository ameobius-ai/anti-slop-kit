# ADR-015: Использование Event Sourcing для обработки заказов

## Статус

Принято (2026-08-01)

## Контекст

Наша система обработки заказов в настоящее время использует традиционный CRUD-подход с единственной таблицей orders. По мере роста объёма заказов до 50 000 заказов в день, мы сталкиваемся с несколькими проблемами:

1. **Требования к аудиту**: Соответствие требует отслеживания всех изменений состояния заказов, но наш текущий журнал аудита неполный и его трудно запрашивать

2. **Сложность отладки**: Когда заказы достигают неожиданных состояний, мы не можем восстановить, как они туда попали

3. **Узкие места производительности**: Высокая нагрузка на запись в таблицу orders вызывает конфликты блокировок в часы пик

4. **Проблемы интеграции**: Нижестоящие системы (склад, доставка, аналитика) нуждаются в разных представлениях данных заказов, что приводит к сложным ETL-конвейерам

Нам нужна архитектура, которая обеспечивает полные журналы аудита, упрощает отладку, улучшает производительность записи и обеспечивает гибкие интеграции.

## Решение

Мы примем event sourcing для обработки заказов. Вместо хранения текущего состояния мы будем хранить append-only журнал всех событий, влияющих на заказ (OrderPlaced, PaymentReceived, OrderShipped и т.д.). Текущее состояние будет выводиться путём воспроизведения событий.

### Ключевые детали реализации

**Хранилище событий**: PostgreSQL с выделенной таблицей order_events
- Столбцы: event_id, order_id, event_type, event_data (JSONB), timestamp
- Индекс на (order_id, timestamp) для эффективного воспроизведения

**Модели чтения**: Материализованные представления для разных потребителей
- orders_current: Последнее состояние для операционных запросов
- orders_analytics: Денормализованное представление для аналитики
- orders_warehouse: Упрощённое представление для складской системы

**Обработчики событий**: Асинхронные воркеры, обновляющие модели чтения при возникновении событий

**Схема событий**: Валидация JSON Schema для всех типов событий

## Последствия

### Положительные

1. **Полный журнал аудита**: Каждое изменение состояния записывается с временной меткой и контекстом
2. **Временные запросы**: Можно восстановить состояние заказа в любой момент времени
3. **Производительность записи**: Append-only записи быстрее и избегают конфликтов блокировок
4. **Гибкие интеграции**: Каждая нижестоящая система может построить свою собственную модель чтения
5. **Отладка**: Можно воспроизвести события, чтобы понять, как заказ достиг текущего состояния
6. **Масштабируемость**: Хранилище событий можно партиционировать по order_id для горизонтального масштабирования

### Отрицательные

1. **Сложность**: Разработчики должны мыслить в терминах событий, а не мутаций состояния
2. **Кривая обучения**: Команде нужно обучение паттернам event sourcing
3. **Согласованность в конечном счёте**: Модели чтения согласованы в конечном счёте, а не немедленно
4. **Затраты на хранение**: Хранение всех событий требует больше места, чем CRUD (оценка 3x)
5. **Сложность запросов**: Некоторые запросы требуют воспроизведения событий, что медленнее прямых запросов
6. **Эволюция схемы**: Изменения схемы событий требуют осторожной стратегии миграции

## Рассмотренные альтернативы

### Альтернатива 1: Улучшенное ведение журнала аудита

Добавить комплексное ведение журнала аудита в существующую CRUD-систему.

**Плюсы**: Более простая реализация, знакома команде
**Минусы**: Журнал аудита становится отдельным источником истины, всё ещё есть конфликты записи, не решает проблемы интеграции

**Почему отклонено**: Не решает коренные причины, добавляет сложность без полных преимуществ

### Альтернатива 2: CQRS без Event Sourcing

Разделить модели чтения и записи, но использовать традиционное хранилище состояния для записей.

**Плюсы**: Улучшает производительность чтения, обеспечивает гибкие модели чтения
**Минусы**: Не обеспечивает журнал аудита или временные запросы, всё ещё есть конфликты записи

**Почему отклонено**: Решает только некоторые проблемы, event sourcing обеспечивает более полное решение

## План реализации

**Фаза 1 (2026-08-01 по 2026-08-15)**: Доказательство концепции
- Реализовать схему хранилища событий
- Мигрировать 1% заказов на event sourcing
- Измерить производительность и операционное влияние

**Фаза 2 (2026-08-16 по 2026-09-15)**: Постепенное развёртывание

- Мигрировать 50% заказов (2026-09-01)
- Мигрировать 100% заказов (2026-09-15)

**Фаза 3 (2026-09-16 по 2026-10-15)**: Оптимизация
- Настроить производительность обработки событий
- Оптимизировать запросы моделей чтения
- Реализовать стратегию архивации событий
